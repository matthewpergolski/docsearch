# End-to-end verification

`scripts/verify.sh` proves that the real `docsearch` command line works on the current default pipeline. It runs the static checks, then drives `sync`, `meta`, `search` (with and without filters) and `eval` on a small fixture in a scratch folder, and checks the results. It drives `sync`, `search` and `eval` once more with `models.backend: api` against a stand-in model server. It syncs and searches an old Word file (`.doc`) next to an empty file. It also proves that an eval mode that is not built yet stops before it does any work. It checks the search page and drives `docsearch serve`. One command gives one PASS or FAIL.

## What it checks

1. Static checks in the repository:
   - `uv run ruff check src tests scripts`
   - `uv run ruff format --check src tests scripts`
   - `uv run python -m unittest discover -s tests`
2. Paths. Every `docsearch` path (data, corpus, parsed, index, cache, results, sync state, logs, chunks, page images, file details) resolves inside the scratch folder. If one does not, the script stops before it runs any command.
3. `uv run docsearch sync --full` on the fixture folder. The check reads the sync state database and requires status `ok` for each fixture file. A second check reads the file details that `sync` wrote (`work/meta.jsonl`, copied to `evidence/meta_after_sync.jsonl` right after the step) and requires one row per fixture file, equal to `tests/fixtures/verify/meta.expected.jsonl`: title, author, created and modified dates, date source, folder and file name.
4. `uv run docsearch meta`. It writes `work/meta.jsonl` again from inside the files. The check requires the same rows.
5. `uv run docsearch search "How many days of paid leave does a new baker get each year?"`. The output groups the hits by file. The check requires `verify/handbook.docx` as the first result, its rank line to show `Brindlewick Bakery staff handbook | 2024-03-04` (title, date), and each file in one result group only. The same search with `--json` writes `evidence/search.json` (status lines go to `search_json.txt`). The JSON check requires the keys `query`, `confident`, `answer`, `groups` and `chunk_ids`; `verify/handbook.docx` as the first group; every group with `rank` (1, 2, 3 and so on), `file`, `format`, `name`, `date`, `period` and `pages`; every page with `page`, `rank`, `title`, `snippet`, `score` and `scorer` (`rerank`, `page` or `fused`), a rank inside the hit list and no `File:` at the start of the snippet; no answer (the run does not pass `--agent`); and the same files in the same order as the text output.
6. The same search with `--format xlsx`. The check requires at least one result, and every result of format `xlsx` in `work/meta.jsonl`.
7. The same search with `--after 2025-01-01`. The check requires at least one result, a date on or after 2025-01-01 on the rank line of every result, and no `verify/handbook.docx` (dated 2024-03-04). The CSV file has no date of its own, so it must not appear either.
8. `uv run docsearch eval --full --visual pplx-v2-late --fusion format_aware --mode plain`. Plain mode sets `enrich.llm` and `agent.mode` to `off` for the run. With the default `--abstain threshold`, the eval calls no LLM. Only an explicit `--abstain judge` or `gated` without `--judge-cache-only` calls the abstention judge, and verify never passes those flags. This command runs the default pipeline as `hybrid_visual_fa_pplx-v2-late_rerank` and a no-rerank run for comparison. The check reads the default run in `results/runs.csv` and its per-question file `results/runs/<run_id>.jsonl`. It requires all fixture questions, no box subset, no mode in the settings JSON of the run notes (a plain run records none, so it still matches older runs as a reference), and the gold unit at rank 1 for each question.
9. Models through an API (README "Models through an API"). The script starts `scripts/model_server.py --fake` on a free port on 127.0.0.1. This server answers `/v1/embeddings` and `/rerank` with deterministic stand-ins (hashed word counts as 64-wide vectors, word overlap as scores). It loads no model and uses no network. With `DOCSEARCH_MODELS_BACKEND=api` and its own work folders under `<root>/api/`, the script runs `sync --full`, `search` (the same query) and `eval --full --runs baseline_hybrid_rerank --name api_text --mode plain`. Then it runs `search` with the api settings on the index of step 3 (built with Qwen3-Embedding, 1024 wide), and this search must stop. The checks require: requests on both routes in the server log, no `loading embedder` or `loading reranker` line in the output of the three api steps, the run `api_text` in `<root>/api/results/runs.csv` with device `api` over all fixture questions, `verify/handbook.docx` as the first hit of the api search, and a non-zero exit with `was built with ... dims` from the last search.
10. `uv run docsearch eval --full --visual pplx-v2-late --fusion format_aware --mode enrich`. The enrich eval mode is not built yet, so the command must stop. The check requires a non-zero exit code, the message `the enrich layer is not built yet (a later phase builds it)`, and no new or changed file in the scratch folder (no run, no log). When a later phase builds the enrich layer, change this step to the next mode that is not built, or remove it.
11. `uv run docsearch eval --full --visual pplx-v2-late --fusion format_aware --agent-research`. The research step (row D1 in `decisions.tsv`) works only in agent mode, so the command must stop. The check requires a non-zero exit code, the message `--agent-research needs --mode agent; nothing was run`, and no new or changed file in the scratch folder. The step needs no LLM.
12. `uv run docsearch eval --full --visual pplx-v2-late --fusion format_aware --agent-deck`. The deck gate (row D2 in `decisions.tsv`) works only in agent mode, so the command must stop. The check requires a non-zero exit code, the message `--agent-deck needs --mode agent; nothing was run`, and no new or changed file in the scratch folder. The step needs no LLM.
13. Old Word files (`.doc`). The script makes `handbook.doc` from the fixture `handbook.docx` with LibreOffice (`soffice --convert-to doc`) or, when `soffice` is not on `PATH`, with macOS `textutil -convert doc`. It puts the file next to a 0-byte `empty.doc` in `<root>/doc/corpus/`, then runs `sync --full` and `search "How many days of paid leave does a new baker get each year?" --json` with their own work folders under `<root>/doc/`. The check requires: the sync output says `empty (0 bytes), skipped: 1` and names `empty.doc`; status `ok` for `verify/handbook.doc` in the sync state database, and no row for `empty.doc`; status `ok` and more than 0 characters for `verify/handbook.doc` in `parse_log.csv`; and `verify/handbook.doc` as the first group of the JSON. When neither `soffice` nor `textutil` is on `PATH`, the summary has the line `SKIP doc: no soffice or textutil on PATH, so no .doc was made and the .doc check did not run`, and the run can still pass.
14. The search page (`ui/`). `bun install --frozen-lockfile`, `bunx biome check .`, `bun test src`, a type check and a build into `<root>/ui_dist`, then `bunx playwright test` on that build: 6 tests in 4 projects (light and dark, desktop and phone size) with the API mocked. Playwright output goes to `evidence/ui_e2e/`. When `bun` is not on `PATH`, the summary has the line `SKIP ui: no bun on PATH, so the page was not linted, tested or built`.
15. `uv run docsearch serve` on a free port of 127.0.0.1, with the page from step 14. One search through `GET /api/search` writes `evidence/web_search.json`, `GET /` writes `evidence/web_index.html`, `GET /api/file?file=verify/handbook.docx` (the first hit) writes `evidence/web_file.bin`, `GET /api/config` writes `evidence/web_config.json`, and the same search through `GET /api/search/stream` (what the page uses) writes `evidence/web_stream.ndjson`. The check requires the keys `results`, `notes` and `terms`; `results` equal to the JSON of step 5 (the same search, so no ranking change); the query terms; the built page with its assets at `/`; the fixture's `handbook.docx` (or a PDF copy of it) from `/api/file`; `"ready": true` from `/api/config` (the models loaded at start); and a stream of JSON lines that ends with `done` and the same results. When the `ui` extra is not installed, the summary has the line `SKIP web: the ui extra is not installed (uv sync --extra ui), so docsearch serve was not driven`.
16. Isolation. Nothing in the repository's `data/`, `corpus/`, `work/`, `results/` or `logs/` changed during the run. These folders can hold hours of compute.

The fixture is in `tests/fixtures/verify/`. It is a fictional small bakery: a Word handbook, a 2-page PDF report, a workbook with 2 sheets, and a CSV supplier list. There are 6 questions. Each answer is in one file only, and the two PDF questions are on different pages. So each question has one clear gold unit: a page for the PDF, a file for the other formats. The Word file, the workbook and the PDF each have a title, an author and a date in their own properties (2024-03-04, 2026-01-05 and 2025-09-30). The CSV file has none. LibreOffice keeps the Word title in the PDF but writes the conversion time as its creation date, so the script writes the report's date in its place. To change the fixture, edit `scripts/make_verify_fixture.py` and run `uv run python scripts/make_verify_fixture.py`. The script checks that each answer is in one unit only, and that the PDF has the expected title, author and date. It also writes `meta.expected.jsonl`. The content is the same on each run, but the bytes of the Office files and the PDF change (zip and PDF timestamps).

The run does not need an LLM. The script removes the API key variables (`*_API_KEY`, `ANTHROPIC_*`, `OPENAI_*`, `XAI_*`, `GROQ_*` and similar) for the run. It also removes inherited `DOCSEARCH_*` overrides, except `DOCSEARCH_DEVICE`, so that the run uses `docsearch.yaml` as it is.

What it does not check:
- Search quality. With 4 files and 6 questions, the right file is easy to rank first, so a change that makes search worse on real collections can still pass. A PASS means that nothing is broken. To judge whether a change helps or hurts search, run the full evaluations and the paired bootstrap (see `CONTRIBUTING.md`).
- The vision page reranker (`search.page_reranker`) reorders slide pages only. The fixture has no slides, so this model is not loaded.
- Gated abstention needs an LLM judge and a custom question set. It is not part of the run.
- `answer` needs an LLM. It is not part of the run.
- A real model server (TEI, vLLM, Infinity) and search quality through an API. The stand-in server proves the request shapes, that no local embedder or text reranker loads, and the index guard. The proof against the real models is a separate run (`scripts/model_server.py` without `--fake` and `scripts/api_match.py`).
- A second run on the same `VERIFY_DIR` finds the files unchanged, so `sync` does not parse them again. Use a new folder (the default) for a full proof.
- The `--folder` filter. The fixture files are all at the top of the folder, and a subfolder would change the document ids the questions use. The unit tests cover it.
- That a filter reaches past the unfiltered top results. The fixture has 4 files, so every file is near the top anyway. The unit tests cover it with 300 documents.

## Requirements

- `uv`. The script runs all Python through `uv run`.
- The models in `docsearch.yaml` that the run loads: the text embedder, the page-image embedder, the text reranker and the Docling layout models. Together they use about 9 GB in the Hugging Face cache [measured on one machine]. If they are not in the cache, the first run downloads them and needs network access.
- LibreOffice (`soffice` on `PATH`). `sync` uses it to render Word and PowerPoint pages. `scripts/make_verify_fixture.py` also uses it to write the PDF. The `.doc` check uses it to make and convert the `.doc`, or macOS `textutil` when `soffice` is missing. With neither, that check is skipped.

- Optional: Bun (for step 14) and the `ui` extra (`uv sync --extra ui`, for step 15). Without them the steps are skipped and named in the summary. Step 14 also needs the Playwright browser (`cd ui && bunx playwright install chromium`).

`scripts/verify.sh --doctor` is a read-only check of these requirements. It shows `uv`, `soffice`, the fixture files, and each model the commands load, with `ok` or `MISSING`.

## How to run

```sh
scripts/verify.sh                 # the full run in a new temporary folder
scripts/verify.sh --clean         # the same, then remove the scratch state and keep the evidence
VERIFY_DIR=/tmp/dsv scripts/verify.sh
scripts/verify.sh --doctor        # read-only requirements check
```

Options:
- `VERIFY_DIR` sets the scratch folder. The default is a new folder from `mktemp -d`. The script refuses a folder in the repository's `data/`, `corpus/`, `work/`, `results/` or `logs/`, the repository itself or a folder above it, and a folder that is not empty and was not made by `verify.sh`.
- `--clean` or `VERIFY_CLEAN=1` removes the scratch state after the run. The `evidence/` folder stays.
- `--sabotage` or `VERIFY_SABOTAGE=1` changes the gold of question `verify-06` from `verify/suppliers.csv` to `verify/handbook.docx` in the scratch copy of the questions. It also sets `ingest.doc_converter` to `off` for the `.doc` sync, so `sync` skips `handbook.doc`. The run must then fail on `verify-06` and on the `.doc` check (no state row, no parse log row, no search result). Use it to show that the checks can fail.

The exit code is 0 when all checks pass, 1 when a check fails, and 2 when the script refuses to start.

## Expected time

About 110 seconds on an Apple-silicon laptop with 32 GB and all models in the cache [measured: 112 s in 1 full run with the `--json` search step, which takes about 9 s; 93 s and 94 s in 2 runs before it]. The API steps add about 13 s: `api_sync` 8 to 9 s, `api_search` and `api_eval` 2 s each, the guard search 3 s [measured]. `sync` takes about 20 s, the first `search` and `eval` about 13 s each, each filtered `search` 7 to 9 s, `meta` 1 s, and the static checks about 7 s [measured]. The `--mode enrich` step stops in less than 1 s [measured]. The `.doc` steps add 31 to 35 s: `doc_build` 2 to 3 s, `doc_sync` 16 to 18 s, `doc_search` 12 to 15 s; the full run took 141 s and 147 s with them [measured: 2 runs]. The page and `serve` steps add about 30 s: the `ui_*` steps about 7 s (Playwright 5 s), `web_search` 16 s, as it waits for `serve` to load all four search models at start; the full run took 168 s [measured: 2 runs; 151 s before the start-up load]. Most of the time is model loading. A first run that downloads the models takes longer.

## Evidence

The script writes the evidence to `<root>/evidence/` and prints this path at the end:

- `summary.txt`: the commit, the scratch folder, the sabotage setting, one PASS or FAIL line for each step and each check, the wall time, and the result.
- `<step>.txt` for each step (`ruff_check`, `ruff_format`, `unittest`, `paths`, `sync`, `meta`, `search`, `search_json`, `search_format`, `search_after`, `eval`, `api_sync`, `api_search`, `api_eval`, `api_guard`, `eval_unbuilt`, `doc_build`, `doc_sync`, `doc_search`, `check_sync`, `check_meta_sync`, `check_meta`, `check_search`, `check_search_json`, `check_filter_format`, `check_filter_after`, `check_eval`, `check_eval_unbuilt`, `check_api`, `check_api_search`, `check_doc`, `check_isolation`): the command, its output, its exit code and its time. The summary has no step line for `eval_unbuilt` and `api_guard`, because those commands must fail. The `check_eval_unbuilt` and `check_api` lines judge them.
- `api_server.txt` and `api_requests.jsonl`: the stand-in server's start line and one JSON line per request (route, number of texts, seconds).
- `meta_after_sync.jsonl`: the file details as `sync` wrote them, before `docsearch meta` writes them again.
- `search.json`: the stdout of the `--json` search (the grouped results as JSON).
- `doc_search.json`: the stdout of the `--json` search on the `.doc` folder.
- `results/`: a copy of `runs.csv` and the per-question files.
- `logs/`: a copy of the `docsearch` run logs. Warnings go to these logs, not to the screen.

## How to read a failure

Start with `summary.txt`. Find the first FAIL line.

- `FAIL step <name> (exit N, ...)`: the command failed. Read `<name>.txt` for the error. If `sync` fails, the script does not run `search` and `eval`, and their checks fail too.
- `FAIL step unittest`: read `unittest.txt`. The tests run as they do for a developer, in the terminal that started the script. Tests must not write to the repository's `data/`, `corpus/`, `work/`, `results/` or `logs/`. If a test does, the isolation check fails.
- `FAIL paths: ...`: a `docsearch` path is outside the scratch folder. Nothing ran. Look for a change in how `docsearch.yaml` or `src/docsearch/config.py` finds paths.
- `FAIL sync: <file> status <status> (<error>)`: the parse of that file failed or did not finish. The run log in `logs/` has the details.
- `FAIL search: first result is ... (got ...)`: read `search.txt` for the grouped results. `FAIL search: first result shows ...`: the rank line of the first result (title, date) changed. `FAIL search: each file is one result group`: a file shows in two groups. For both, read `src/docsearch/display.py` (`group`, `render`).
- `FAIL json: ...`: read `search.json` and `search_json.txt`. A JSON parse error with status lines in `search.json` means that a status line reached stdout: check the `--json` redirect in `src/docsearch/cli.py` (`main`). A shape FAIL means that the fields in `src/docsearch/display.py` (`ResultGroup`, `PageHit`, `Results`) changed.
- `FAIL meta (<command>): ...`: the file details differ from `tests/fixtures/verify/meta.expected.jsonl`. The `got` part names each field that differs. If the fixture was rebuilt, check that `scripts/make_verify_fixture.py` still writes the titles and dates. If not, read `src/docsearch/meta.py` (`EXTRACTORS`).
- `FAIL filter: ...`: read `search_format.txt` or `search_after.txt`. A hit of the wrong format or date means that the filter did not reach retrieval (`search.search`, `Retriever.candidates`). No hit at all means that no file passed the filter: check `work/meta.jsonl` in the scratch folder.
- `FAIL eval: <qid> gold <unit> at rank N (first: <unit>)`: the default pipeline ranked another unit first for that question. Read `results/runs/<run_id>.jsonl` for the full top 10. In a sabotage run, a FAIL on `verify-06` is the expected result.
- `FAIL refusal: ...`: `eval --mode enrich` did not stop as it must. Read `eval_unbuilt.txt`. Exit 0 or a missing message means the mode check in `src/docsearch/eval.py` (`MODES`, `apply_mode`) changed. A `changed:` list names the files that the command wrote before it stopped.
- `FAIL api: ...`: read the step file it names (`api_sync.txt`, `api_search.txt`, `api_eval.txt`, `api_guard.txt`) and `api_server.txt`. No requests on a route means that the client did not call the server: check `models.load_embedder` / `models.load_reranker` and the URLs. A `loaded:` list means that a command in api mode loaded a local model. A guard FAIL means that `index.check_model` did not stop the search.
- `FAIL doc: ...`: read `doc_sync.txt`, `doc_search.txt` and `doc_search.json`. A missing `empty` line means that the 0-byte rule in `src/docsearch/sync.py` (`make_plan`, `notes`) changed. State `missing` with a `.doc file skipped` line means that no converter was found (`src/docsearch/docconv.py`, `pick`). State `failed` or a parse log status other than `ok` means that the conversion or the parse failed: the error is in the state database and in `<root>/doc/logs/`. In a sabotage run, these FAIL lines are the expected result.
- `FAIL isolation: nothing in the repo's <dir>/ changed during the run (changed: ...)`: a file in that folder changed while the script ran. Another process can also cause this, for example an experiment that runs at the same time.
